# Phase 0 Research: Public SDK Release 0.1.0

## Decision 1: Publish the Android AAR to Maven Central

**Decision**: Use Maven Central as the canonical public repository with coordinates
`info.marcin.usbhost:usb-host-for-android:0.1.0`.

**Rationale**: Maven Central is directly supported by Gradle/Android consumers and is the standard
repository for public JVM and Android libraries. Google Maven serves Android/Google platform
artifacts and is not an open third-party publication target. The Gradle Plugin Portal is for Gradle
plugins; this project publishes an Android AAR, not a plugin.

**Alternatives considered**:

- GitHub Packages: useful as a secondary private/authenticated registry, but requiring credentials
  for ordinary consumers makes it a poor canonical public dependency source.
- JitPack: simple but builds artifacts on demand and gives weaker control over signed immutable
  release metadata.
- Google Maven / Gradle Plugin Portal: deliverable type does not match their publication purpose.

## Decision 2: Use the Central Publisher Portal, not legacy OSSRH

**Decision**: Publish through the Central Portal API using Central user-token credentials and
automatic release after validation.

**Rationale**: Sonatype's current documentation states that the legacy OSSRH path is retired and that
Gradle publishers must use a Portal-capable community integration or the API. New automation must
not embed the obsolete `oss.sonatype.org`/`s01` endpoints.

**Alternatives considered**:

- Legacy OSSRH staging: retired and unsuitable for a new 2026 release.
- Custom Portal API client: possible, but recreates bundling, polling, error mapping, and retry logic.
- Maven wrapper solely for publishing: adds a second build model and risks divergence from AAR/Prefab
  metadata generated by AGP.

## Decision 3: Use Vanniktech Gradle Maven Publish Plugin 0.37.0

**Decision**: Apply `com.vanniktech.maven.publish` 0.37.0 to the Android library module.

**Rationale**: It supports Android libraries, sources/documentation artifacts, POM configuration,
in-memory signing, and the Central Portal workflow. Version 0.37.0 is the current upstream release as
of 2026-08-09. It avoids bespoke Portal upload code and integrates with the existing Gradle build.

**Alternatives considered**:

- Raw `maven-publish` + signing + custom Portal upload: fewer plugin dependencies, but much more
  release code and more ways to create an invalid Central bundle.
- JReleaser: capable but introduces an additional release model and configuration surface not needed
  for one AAR.

## Decision 4: Use AGP 9.2 built-in Kotlin and Jetpack Compose

**Decision**: Keep AGP 9.2.1/Gradle 9.4.1/JDK 17, use AGP's built-in Kotlin support, apply only the
Compose compiler plugin 2.3.21, and use Compose BOM 2026.06.01 with Material 3.

**Rationale**: Official Android documentation identifies AGP 9.2 and Gradle 9.4.1 as compatible and
AGP 9.0+ as providing built-in Kotlin. Compose is Kotlin-only and offers a concise, state-driven UI
that can look professional without introducing XML/view-binding boilerplate. The BOM keeps Compose
libraries aligned.

**Alternatives considered**:

- Java/XML sample: already exists but does not satisfy the modern Kotlin example requirement.
- Kotlin/XML Material Views: viable and lighter compiler setup, but more lifecycle/UI synchronization
  code for the same stateful device console.
- Multiplatform UI: unrelated to the Android-only 0.1.0 release and expands scope prematurely.

## Decision 5: Separate safe sample operations from future programmer operations

**Decision**: The 0.1.0 sample offers device scan, permission, connect, target/probe information,
bounded 256-byte read, disconnect, and logs. It does not render or call write/erase/debug-state APIs.

**Rationale**: This produces a useful programmer-style console while respecting the existing public
read-only safety boundary and allowing hardware smoke tests without mutating the target.

**Alternatives considered**:

- Full programmer clone: exceeds the time/safety scope and would require new public destructive APIs.
- Discovery-only sample: safe but too small to prove target connection and native integration.

## Decision 6: GitHub-hosted CI plus a pinned OCI runner image

**Decision**: Standard workflows run on hosted Ubuntu runners and cache Gradle/Android artifacts.
Provide a pinned Dockerfile for local parity and publish its image to GitHub Container Registry.
Support an optional Docker Hub mirror only when `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` exist.

**Rationale**: GHCR can publish from this public repository using `GITHUB_TOKEN`, so it is automatable
without an unrelated registry account. Docker Hub cannot be pushed safely without user credentials.
The image pins JDK, command-line tools, SDK, NDK, CMake, and Ninja and is reusable locally.

**Alternatives considered**:

- Docker Hub only: would block implementation on unavailable third-party credentials.
- Container-only CI: startup/image pulls may be slower than hosted setup plus Gradle caches for normal
  pull requests; the container remains valuable for reproducibility and local testing.
- Self-hosted runner: creates operations and trust requirements inappropriate for a public repo.

## Decision 7: Release on an approved main-contained version tag

**Decision**: Normal changes flow task branch → `dev`; an approved PR promotes `dev` → `main`; tag
`v0.1.0` must point to a commit contained in `main`, match Gradle version 0.1.0, and pass full CI before
Central upload and GitHub release creation.

**Rationale**: Branch containment and version checks prevent an arbitrary tag or development commit
from publishing. GitHub environments can add maintainer approval and isolate publication secrets.

**Alternatives considered**:

- Publish on every `main` push: risks accidental duplicate or unintended releases.
- Publish from `dev`: contradicts the requested release policy and weakens promotion control.
- Manual local publish: provides poor provenance and requires sensitive credentials on workstations.
